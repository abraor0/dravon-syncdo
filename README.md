# Dravon SyncDo

Internal task board for Grupo Dravon. Members sign in, manage their own tasks, and follow teammates' boards in real time.

## Stack

- React 19 + TypeScript + Vite
- Tailwind CSS v4
- TanStack Query (server state) and Zustand (session + persisted board layout)
- Supabase (auth, Postgres with RLS, realtime)
- Deployed on Vercel as a SPA

## Features

- **My Tasks**: your own tasks, created inline.
- **Company View**: one column per teammate; columns and per-column sort order persist in localStorage.
- Inline editing of title, description, and priority; tasks can be handed over to another member.
- Completion audit (`completed_at`, `completed_by`) and a metrics bar filtered by Today / Week / Month / All.
- Live sync of every change through Supabase realtime.

## Data model and permissions

`tasks.assignee` and `tasks.completed_by` store the user's **email**, which is what RLS checks against.

| Action | Allowed for |
| --- | --- |
| Read | Any signed-in user |
| Create | Signed-in user, only with themselves as assignee |
| Update / delete | The current assignee (an update may reassign the task) |

The database also owns the fields members shouldn't control (migration `20261120000000_harden_tasks.sql`):

- `status` is `pending` or `completed`; `priority` is `low`, `medium` or `high`.
- New tasks always start as `pending`.
- `completed_at` and `completed_by` are set by the server when a task is completed (its time, the signed-in member) and cleared when it is reopened. Values sent by the client are ignored.
- `created_at` is set by the server and never changes.
- A task can only be handed to an existing member.

These rules apply to signed-in members. Direct database access (migrations, the seed, admin fixes) is not restricted.

`get_all_users()` lists members for the column picker and is callable only by signed-in users.

Accounts are created by an admin in the Supabase dashboard; public sign-up is disabled.

## Setup

Requires Node.js 22.12+ and Docker. Everything runs locally; no Supabase account is needed.

1. `npm install`
2. `npx supabase start`: starts the local Supabase stack and applies `supabase/migrations` and `supabase/seed.sql`.
3. `cp .env.example .env.local`, then replace `YOUR_LOCAL_PUBLISHABLE_KEY_HERE` with the **Publishable** key printed by `npx supabase status`. It is a local-only development key generated by the Supabase CLI.
4. `npm run dev` and sign in with `example1@example.com` / `password123` (or `example2@example.com`).

To reset the database to the seed: `npx supabase db reset`. To stop: `npx supabase stop`.

## Scripts

- `npm run dev`: dev server

- `npm run typecheck`: TypeScript only
- `npm run lint`: ESLint

- `npx supabase test db` (or `npm run test:db`): database tests

## Testing

Three layers, from fastest to slowest:

| Layer | Where | Runs against |
| --- | --- | --- |
| Unit and component (Vitest + React Testing Library) | `src/**/*.test.ts(x)`, next to the code | jsdom; Supabase is mocked, so no stack is needed |
| Database (pgTAP) | `supabase/tests/database/*.test.sql` | the local Postgres; each file runs in a transaction that is rolled back |
| End-to-end (Playwright, Chromium) | `e2e/*.spec.ts` | the app on a Vite dev server (port 5199) and the local stack |

Database tests are grouped by rule: `selections`, `insertions`, `updates`, `deletions`, `list_users`, `columns` (allowed values) and `server_fields` (the fields the server owns). They act as a member by setting the same role and JWT claims PostgREST would, using the helpers in `supabase/tests/database/_session.psql`.

E2E specs follow the main flows: `auth`, `tasks`, `filters` and `realtime`.

### Running everything

After the [Setup](#setup) steps (stack running, `.env.local` in place):

```sh
npx playwright install --with-deps chromium   # once; on Linux this installs system libraries with sudo
npm test
npx supabase test db
npm run test:e2e
npx playwright show-report                    # after a failure: HTML report with traces
```

Notes on the E2E suite:

- It only runs against a local stack: it refuses any `YOUR_SUPABASE_URL` or database URL that isn't `localhost` / `127.0.0.1`.
- Test data is written straight to the local Postgres (`postgresql://postgres:postgres@127.0.0.1:54322/postgres`, the stack's default; override with `E2E_DATABASE_URL`). Every task a test creates has a unique `[e2e …]` title prefix and is deleted when the test ends, so the seed data is never changed and no database reset is needed.
- Each seeded member signs in once per run through the auth API; the auth spec also signs in through the login form. Local auth allows 30 sign-ins per 5 minutes, so many back-to-back runs can hit that limit.

## Architecture

Feature-based modules.

- `src/features/<feature>/{components,hooks,services}`: feature code
- `src/components`, `src/hooks`, `src/services`: shared across features
- `src/pages`: thin route containers
